# Контракт ожидания фоновой работы, v1

Расширение реализовано для **ACP v1**. Для явного выбора протокола можно передать `CLAUDE_AGENT_ACP_PROTOCOL=v1`. Base upstream также поддерживает другие ACP surfaces, но этот собственный RPC добавлен в обработчик v1.

## Согласование

Клиент предлагает расширение и AIR capabilities в `initialize`:

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "initialize",
  "params": {
    "protocolVersion": 1,
    "clientInfo": {"name": "example-client", "version": "1.0.0"},
    "clientCapabilities": {
      "_meta": {
        "orchestratorBackgroundTasks": 1,
        "jetbrains": {
          "air": {
            "version": 1,
            "capabilities": [
              "asyncTasks",
              "nativeSubagentSessions",
              "sessionFailure"
            ]
          }
        }
      }
    }
  }
}
```

В `result._meta` ответа адаптер добавляет:

```json
{
  "orchestratorBackgroundTasks": {"version": 1}
}
```

Это фрагмент metadata, а не полный initialize response. Проверенный клиент также проверяет подтверждение AIR capabilities и `agentCapabilities.sessionCapabilities.close`.

Без `clientCapabilities._meta.orchestratorBackgroundTasks = 1` адаптер не объявляет собственный контракт. Вызов RPC без согласования отклоняется. Обычный `session/close` остаётся безусловным: для успешного drain его нельзя подменять новым RPC с игнорированием ответа.

## Создание и выполнение сессии

Сначала создайте или загрузите сессию стандартными ACP методами, затем передайте `session/prompt`. Расширение не создаёт сессию и не заменяет стандартные методы выполнения.

Во время prompt и после его ответа продолжайте читать ACP stdout и обслуживать уведомления/запросы клиента. Ответ `end_turn` — результат конкретного prompt, а не автоматическое разрешение завершить весь runner. Фоновая работа и автоматические ходы могут продолжаться.

## Снимок

Запрос:

```json
{
  "jsonrpc": "2.0",
  "id": 10,
  "method": "_orchestrator/background",
  "params": {"sessionId": "SESSION_ID"}
}
```

Пример ответа:

```json
{
  "jsonrpc": "2.0",
  "id": 10,
  "result": {
    "version": 1,
    "sessionId": "SESSION_ID",
    "pending": true,
    "modelBusy": false,
    "token": "OPAQUE_SNAPSHOT_TOKEN",
    "tasks": [
      {"id": "TASK_ID", "state": "running", "autonomous": false}
    ],
    "closed": false
  }
}
```

Значения ID и token в примере условные.

| Поле | Смысл |
| --- | --- |
| `version` | Integer `1` |
| `sessionId` | Сессия запроса |
| `pending` | Есть учтённая активная работа: native tasks, дети, ходы, SDK running state или обработка SDK event |
| `modelBusy` | Модель/очередь ходов/автоматический ход/обработка SDK event заняты; не равнозначно наличию работающего shell |
| `token` | Непрозрачный string для условного закрытия. Передавайте его обратно без разбора и модификации |
| `tasks` | Async task registry; native и synthetic autonomous-turn записи |
| `tasks[].state` | `running`, `paused`, `completed`, `failed` или `stopped` |
| `tasks[].autonomous` | `true` у записи, представляющей автоматический ход модели |
| `closed` | `false` для обычного status запроса; `true` только у принятого conditional close |

Snapshot включает также held tasks, spawn которых ещё не доставлен клиенту. Дочерние агенты, SDK running state и очередь учитываются в `pending`/token, хотя не обязаны быть отдельными элементами массива `tasks`. Поэтому пустой массив или отсутствие `running` в нём **не заменяет проверку `pending`**.

Token зависит от поколения обработанных SDK-сообщений и текущего снимка задач/детей. Обрабатывайте его как opaque string. Polling сам по себе не меняет поколение.

Сессия должна существовать и оставаться live. Для неизвестной, завершившей SDK stream или torn-down сессии RPC возвращает ошибку; это не подтверждение успешного закрытия.

## Что означает terminal state

В negotiated-режиме исчезновение задания из replace-semantics SDK списка **не** вызывает синтетический `stopped`. Адаптер продолжает считать его активным до явного terminal event.

`failed` фоновой команды — результат для анализа моделью: она может прочитать output и решить, нужен ли retry. Это не автоматическое разрешение успеха и не автоматически фатальная ошибка сессии. `sessionFailure` остаётся отдельным механизмом. `stopped` также требует учитывать, зачем задача была остановлена; клиенту следует дать модели проверить результат исходной задачи.

В ordinary upstream-режиме без согласования патч не изменяет прежнюю level-reconciliation политику.

## Условное закрытие

После устойчивого idle клиент запрашивает закрытие с token последнего снимка:

```json
{
  "jsonrpc": "2.0",
  "id": 11,
  "method": "_orchestrator/background",
  "params": {
    "sessionId": "SESSION_ID",
    "close": true,
    "token": "OPAQUE_SNAPSHOT_TOKEN"
  }
}
```

Адаптер в одном синхронном участке проверяет актуальный снимок и состояние. Если есть pending work или token не совпадает, ответ содержит `closed:false`. Такой отказ не отменяет работу; продолжайте drain.

Если условия выполнены, адаптер помечает сессию закрывающейся, запрещает новые prompt, выполняет teardown и возвращает `closed:true`. До подтверждения нельзя закрывать SSH/stdin как будто работа уже завершена.

После подтверждения клиент должен завершить stdio-соединение, дочитать поток, дождаться кода выхода и проверить очистку своего runner. Оставшаяся или неподтверждённая работа не должна превращаться в успешный результат только из-за `closed:true`.

## Рекомендованный алгоритм клиента

```text
initialize: предложить и проверить контракт
session/new или session/load
session/prompt

пока не истёк общий deadline:
    читать ACP updates и обслуживать встречные запросы
    получить snapshot
    если модель занята:
        продолжить ожидание
    если есть native работа:
        ждать её завершения
        при необходимости дать модели ход проверки/остановки ненужных servers
    если результаты native задач ещё не проверены:
        передать проверочный prompt в ту же сессию
        после ответа снова проверить snapshot
    если состояние устойчиво в течение выбранного quiet interval:
        запросить close с последним token
        если closed=false: продолжить ожидание
        если во время close пришла новая работа: не считать это успешным drain
        если closed=true: дождаться штатного выхода и подтвердить очистку
```

Конкретные poll interval, quiet interval, проверочные prompt и общий timeout задаёт клиент. Проверенная интеграция использует quiet=60 секунд, один reconciliation prompt для неизменившейся работы после 30 секунд idle и не вводит дополнительные пределы «три prompt / 300 секунд». Это свойства интеграции, не встроенные таймеры этого RPC.

## Границы атомарности

Проверка token и запрет новых prompt защищают от уже наблюдаемой адаптером смены состояния. SDK-события ещё могут находиться в пути; quiet interval и продолжение чтения нужны и после первого `end_turn`. Контракт не является распределённой транзакцией с провайдером и не учитывает произвольные процессы вне native registry.
